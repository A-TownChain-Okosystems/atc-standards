# SCR-0130 — ATC Function & Change Evidence Architecture

| Field | Value |
|---|---|

| Standard | ATC-STD-644 |

## Motivation

The existing standards define requirements traceability, change control, audit records and evidence, but the ecosystem needs one machine-checkable contract that connects component, function and change evidence down to an exact source commit and CI execution.

The target rule is:

> No claim without evidence. No evidence without identity. No verification without exact source binding. No release status without complete required traceability.

## Proposed change

Introduce **ATC-STD-644 — Function & Change Evidence Standard** as the canonical evidence model for:

- Component Evidence
- Function Evidence
- Change Evidence
- Implementation identity
- Specification/documentation linkage
- Test linkage
- exact-commit CI evidence
- E2E/audit/release evidence
- bidirectional traceability
- change-impact gates

## Core invariants

1. A function claim MUST resolve to a stable Function ID.
2. An implementation MUST identify repository, path, module/symbol and exact commit SHA.
3. CI evidence MUST identify the exact commit SHA, workflow run, job, step and result.
4. CI evidence for one SHA MUST NOT be reused as verification for another SHA.
5. Behavior-changing changes MUST undergo specification/documentation/test impact analysis.
6. API/ABI changes MUST record their specification/documentation/test impact.
7. Documentation-only and test-only changes MUST NOT be represented as implementation changes.
8. Required traceability links MUST be complete before a release-ready claim.
9. Status and traceability are separate dimensions.
10. Missing evidence MUST remain NOT_PROVEN/INCOMPLETE rather than being inferred.

## Relationship

Requirement → Specification → Component → Function → Implementation → Change → Test → CI → E2E → Audit → Release.
