## 1. Decision Requested

Authorize a controlled architecture reconciliation to determine and document the normative relationship between:

1. the seven independent product/technology pillars;
2. the system-of-systems architecture and its responsibility domains/layers;
3. normative repository classification and dependency constraints; and
4. cross-cutting control-plane responsibilities and interface contracts.

The reconciliation must produce one explicit, approved authority model and a source-to-source compatibility matrix. It must not silently select one existing document as superior, change normative meaning by implication, or treat this SCR itself as an approval.

**No normative architecture decision is made by this proposal.** Owner decision and the applicable review/approval process under ATC-STD-000 are required before standards, registries, validators or implementation mappings are changed.

## 3. Required Architecture Invariants

The reconciliation must preserve these constraints unless the Owner explicitly decides otherwise through the applicable governance process:

- The seven product/technology pillars remain independently identifiable systems:
  1. ATCLang
  2. ShivaCore Kernel
  3. Aurora AI
  4. A-TownChain Blockchain
  5. ATC-VM
  6. GlobusOS
  7. Genesis Engine
- The seven pillars are **not** asserted to form a single linear runtime chain or a universal parent/child hierarchy.
- Aurora AI and Genesis Engine are not defined as downstream products of GlobusOS.
- A-TownChain Blockchain is not subordinate to ATCLang as a product or authority domain.
- Integration is achieved through explicit interfaces, contracts, authorization boundaries and evidence—not by relocating component ownership.
- Each implementation capability retains exactly one canonical implementation SSOT, as established by the applicable repository ownership records.
- Architecture-layer numbering, repository classification, product taxonomy, runtime ordering and dependency direction must be treated as distinct concepts unless an approved specification explicitly defines their relationship.
- ATC-STD-204 interface and dependency controls remain in force. This SCR does not authorize implicit dependencies or weaken any existing security, CI or governance gate.
- Architecture descriptions are not implementation or verification evidence.

## 4. Reconciliation Work Packages

### 4.1 Establish source authority and scope

For each source, record:
- document type and normative/informative status;
- approval authority, approval evidence and lifecycle state;
- scope and entities governed;
- definitions of layer, pillar, component, repository, dependency and runtime order;
- requirements that are binding versus explanatory diagrams/examples;
- supersession, compatibility and conflict-resolution rules.

Determine whether `ARCHITECTURE.md` is an informative system architecture, a normative architecture contract, or a controlled architecture source referenced by standards. Do not infer normative authority from the filename or the word ACTIVE alone.

### 4.2 Produce a clause-level conflict matrix

At minimum compare:
- AD-026 L0–L7 layer names, definitions and directionality;
- ATC-ARCH-001 vertical dependency diagram and component inventory;
- ATC-STD-202 repository classification and layer assignments;
- ATC-STD-204 declared dependency and interface rules;
- current Ecosystem L0–L7 responsibility domains and X control plane;
- the seven independent product/technology pillars and their authority boundaries.

Every matrix row must identify the source clause, exact source revision, semantic difference, affected consumers, compatibility impact, proposed disposition and approving authority.

### 4.3 Separate architecture taxonomies

Evaluate whether the normative model should explicitly distinguish:
- **Product/Pillar Taxonomy:** independent products and technology systems;
- **System Responsibility Domains:** architectural concerns such as system/network, persistence, consensus, deterministic execution, scaling, protocol/economic services, intelligence and user experience;
- **Repository Governance Taxonomy:** repository type, maturity, canonical ownership and security classification;
- **Runtime/Operational Flows:** actual execution and data-flow sequences, defined only where required by a concrete contract;
- **Cross-Cutting Control Plane:** identity, capability, authorization, policy, governance, cryptography, audit, evidence and compatibility.

A mapping between these taxonomies may be many-to-many. It must not be used to manufacture product dependencies or change SSOT ownership.

### 4.4 Define dependency semantics

Using ATC-STD-204 as a required compatibility input, distinguish:
- compile-time dependency;
- runtime/service dependency;
- protocol or data-contract dependency;
- optional integration;
- governance/specification reference;
- evidence/catalog reference;
- cross-cutting authorization or policy enforcement.

For each declared dependency specify provider, consumer, interface/version, direction, authority owner, failure behavior and validation evidence. A layer label alone must not be treated as proof of a runtime dependency.

### 4.5 Assess existing consumers and migration

Before any normative change:
- enumerate all standards, repository manifests, dependency registries, schemas, validators, CI workflows, generated views, architecture diagrams and product documents that consume AD-026 or the affected layer identifiers;
- identify hard-coded assumptions and compatibility risks;
- define migration and deprecation behavior;
- preserve historical identifiers and decision records;
- prevent partial migrations in which standards, registries and validators disagree.

## 5. Decision Options for Owner Review

The reconciliation team should evaluate, not preselect, at least these options:

**Option A — Separate taxonomies (preferred for evaluation, not approved):** retain product pillars, system responsibility domains, repository classification and runtime flows as distinct models, connected by explicit mapping and interface contracts. Reconcile ATC-STD-202 and ATC-ARCH-001 so their normative scope is unambiguous.

**Option B — Retain AD-026 as the sole normative layer hierarchy:** keep the existing L0–L7 directionality but explicitly limit it to the domain it governs; define product pillars and cross-cutting controls separately and prevent layer numbering from being interpreted as a product dependency chain.

**Option C — Revise the normative architecture model:** replace or materially revise the current hierarchy through a versioned breaking-change process, with complete consumer inventory, migration plan, compatibility controls and explicit Owner approval.

No option may be implemented by editing only the Ecosystem master architecture or only the strategy document. The selected option must be reflected consistently in every affected normative source and its enforcement tooling.
