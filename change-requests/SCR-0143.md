# SCR-0143 — Propose ATC Hybrid Governance Standard

## Identity and allocation status

**SCR-0143 is provisional and pending validation.** The existence of this file or its pull request does not establish that the identifier is formally allocated, accepted, or closed. The SCR identity must be reconciled with the canonical SCR registry and validated by the Owner.

**Current status:** candidate / non-normative

The current standards registry snapshot contains ATC-STD-600 through ATC-STD-607 in the relevant numeric family, but absence of ATC-STD-608 from that snapshot is not by itself proof of availability. Formal allocation must be completed by the registry process; no allocation is performed by this SCR.

## Proposed change

Add a candidate hybrid-governance specification defining:
- central coordination of development and standards;
- independent validator operation and separation of keys/authority;
- consensus governance and protocol upgrade controls;
- deterministic issuance and the 360,000,000 ATC supply ceiling;
- staking, fee and reward accounting requirements;
- constraints on emergency powers and state recovery;
- decentralization measurement and exact-source evidence requirements.

The candidate document is proposed at `proposals/ATC-HGOV-001.md`. It does not claim normative force and does not modify the Standards Registry.

## Motivation

A-TownChain intends to operate as a public blockchain with ATC as its native, freely market-priced cryptocurrency. A hybrid organization/network model requires explicit boundaries so that central development coordination does not become unilateral control over consensus, funds, issuance or canonical history.

## Compatibility and conflicts requiring resolution

1. ATC-STD-NET-006 already defines an upgrade process and an 80% active-staking-power signaling threshold. The candidate preserves that standard and requires explicit reconciliation of its semantics with validator independence and governance approval.
2. The 360,000,000 ATC supply ceiling must be reconciled with all genesis allocations, block rewards, AI-compute mining rewards, PoS validator rewards, halvings, fees and burns.
3. The existing desired automatic staking behavior must distinguish liquid, bonded, unbonding and claimable balances; no hidden lock or undisclosed slashing exposure is authorized.
4. Fee and reward accounting order (same block versus later block/epoch) must be specified deterministically and reconciled with transaction and consensus implementations.
5. Validator independence must be measured using operator, stake, client and infrastructure concentration; validator count alone is insufficient.

No existing approved standard is silently amended by this proposal.

## Security impact

No implementation or security control changes at proposal stage. The candidate requires tests for privileged paths, unauthorized upgrades, unauthorized minting, key-role separation, censorship controls, deterministic recovery and supply invariants.

## Migration impact

No migration is authorized. Any future implementation must identify the authoritative implementation repository and exact module paths, define compatibility and version transitions, prove behavior on testnet, and provide exact-commit CI and artifact evidence.
