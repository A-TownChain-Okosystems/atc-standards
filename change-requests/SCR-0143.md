| Feld | Wert |
|---|---|
| SCR-ID | SCR-0143 |
| Datum | 2026-11-17 |
| Auslöser | Befund beim Einzug von ATC-ARCH-002 (SCR-0142 §10) |

| Betroffene Standards | ATC-STD-000 (freigegeben, v1.3.0) |

## 1. Problem

Die Genehmigungsstelle im Governancestandard ist **ATC-STD-000 §18 (Approval)**.
§18 verlangt Technical Review PASS, Security Review PASS, Architecture Review PASS
und keine offenen kritischen Findings; §14 bis §17 beschreiben die Kette.

§9 desselben Standards regelt dagegen die **Standardstruktur** — die Abschnitts-
reihenfolge eines Standards, nicht seine Freigabe.

Im Bestand wird für die Freigabe dennoch durchgängig §9 zitiert:

- **133 Stellen in 118 Dateien** nennen „ATC-STD-000 §9" als Freigabegrundlage.
- Praktisch ausschließlich betroffen: **freigegebene Standards** (Statuszeilen wie
  „APPROVED (Owner-Sammelfreigabe 07.09.2026, ATC-STD-000 §9)").
- Beispiele: `standards/repository/ATC-STD-201.md` Z. 23,
  `standards/ai/ATC-STD-AI-DEV-001.md` Z. 23 und Z. 217,
  `standards/repository/ATC-STD-204.md` Z. 22 und Z. 167.

Für einen Leser ohne Vorwissen ist damit nicht erkennbar, worauf sich eine
Freigabe stützt. Für die Prüfbarkeit einer Freigabe ist die Angabe der falschen
Stelle ein Mangel, auch wenn die Freigaben selbst wirksam erteilt wurden.

## 2. Warum das nicht einfach korrigiert wird

§30 (Immutability & Auditability) verbietet das nachträgliche Umschreiben
freigegebener Standards. Eine Massenkorrektur von 118 Dateien würde genau das
tun und die Freigabenachweise nachträglich verändern — der Nachweis wäre dann
nicht mehr das, worauf der Owner am 07.09.2026 entschieden hat.

## 3. Optionen

**Option A — Klarstellende Zeile in ATC-STD-000 §9.** Ein Satz: „Die Genehmigung
eines Standards regelt §18; historische Verweise auf §9 in Bestandsdokumenten
meinen diese Stelle." Dazu Versionssprung ATC-STD-000 v1.3.0 → v1.3.1, ein
Registry-Eintrag, ein Anchor-Nachzug. Kosten: eine Datei. Risiko: gering.
Wirkung: der Widerspruch ist an einer Stelle aufgelöst, der Bestand bleibt
unangetastet.

**Option B — Massenkorrektur aller 118 Dateien.** Kosten: 118 geänderte
freigegebene Standards, neue Hashes, neuer Anchor, 504 berührte Registry-Bezüge
in Views. Risiko: hoch, weil §30 verletzt wird und die Freigabenachweise von
damals nachträglich anders lauten als bei der Entscheidung.

**Option C — Nichts tun.** Kosten: null. Risiko: der Fehler wird bei jeder
weiteren Freigabe mitgeschleppt; genau das ist bei ATC-ARCH-002 passiert.

**Empfehlung:** Option A. Sie beseitigt die Ursache der Fehlzitate für alles
Künftige, ohne historische Nachweise zu überschreiben.

## 4. Abnahmekriterien

1. Owner-Entscheid für A, B oder C liegt vor.
2. Bei A: ATC-STD-000 §9 enthält die klarstellende Zeile; Version v1.3.1 in
   Dokument, Metadaten und Registry gleichlautend.
3. Bei A: `registry_view_gate.py` PASS, R13 ohne Waiskind, Anchor nachgezogen.
4. Bei A: keine Datei mit Status APPROVED wird inhaltlich verändert
   (Nachweis: `git diff --stat` berührt nur ATC-STD-000, seine Metadaten und die
   Registry-Zeile).
5. Dieser SCR dokumentiert das Ergebnis; bei C wird er als abgelehnt geschlossen.

## 5. Nicht-Ziele

- Keine Änderung an Anforderungen, Prüfungen oder Gültigkeit einer bestehenden
  Freigabe.
- Keine Neunummerierung der Abschnitte von ATC-STD-000.
- Keine rückwirkende Umdeutung der Freigaben vom 07.09.2026.

## 6. Referenzen

- ATC-STD-000 §9 (Standard Structure), §14 bis §17 (Review-Kette), §18 (Approval),
  §30 (Immutability).
- SCR-0142 §10 (Befund), ATC-ARCH-002 v0.1.2 (zitiert bereits §18).

### 7.6 Pin-Propagation (Folgewirkung der Version)

Die Version 1.3.1 verlangt nach `tools/consistency/version_gate.py`, dass jedes
**aktive** Consumer-Repo den Verfassungsstand exakt führt. Erhoben am 17.11.2026:

| Repo | Stelle | Vorgang |
|---|---|---|
| `a-townchain` | README-Standardtabelle | PR #110 |
| `atc-launchpad` | README-Einleitung + Tabelle | PR #9 |
| `atc-toolchain` | README-Standardtabelle | PR #5 |
| `genesis-chronicles` | README-Standardtabelle | PR #18 |
| `atc-standards` selbst | README (generiert) | in PR #133 enthalten |

**Gate-Korrektur, damit die Prüfung eine Aussage behält:** `version_gate.py` hat
bisher jedes Repo aus `registry/repositories.yaml` als Consumer behandelt, auch
archivierte und eingefrorene. Diese 13 Repos führen ihren kanonischen Stand in
`a-townchain/components/<name>` (SCR-0127) und sind keine Propagationsziele; ein
archiviertes Repo kann technisch gar nicht folgen. Die Prüfung überspringt sie
jetzt **sichtbar** mit `SKIP`-Zeile samt Status und kanonischem Ort. Für aktive
Repos bleibt die Prüfung fail-closed und unverändert streng.

Reihenfolge der Einziehung: erst die vier Pin-PRs, dann PR #133. Vorher kann
`version-gate` nicht grün sein, weil es die READMEs des jeweiligen `main` liest.
