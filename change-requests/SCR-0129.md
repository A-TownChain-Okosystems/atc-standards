# SCR-0129 — Workflow Job Evidence Architecture & Exact-SHA Verification

## 1. Purpose

Dieses SCR erweitert die bestehende Evidence-Governance um ein verbindliches,
workflow- und jobbezogenes Evidence-Modell.

Ein GitHub Actions Workflow-Job darf nicht nur als PASS/FAIL-Signal betrachtet
werden. Der Job ist ein prüfbares Evidence-Objekt mit reproduzierbarer
Zuordnung zu Workflow, Run, Job, getesteter Revision, Steps, technischen
Findings, Architekturvertrag, Root Cause, Minimal Fix und Rerun.

Der bestehende ATC-Standard MAINT-019 definiert bereits ein allgemeines
maschinenlesbares Evidence-Modell, ist aktuell jedoch ausdrücklich
SPECIFICATION_ONLY. Dieses SCR konkretisiert die Workflow-/Job-Ebene und
definiert die Exact-SHA-Anforderung.

## 2. Existing-First Finding

Bereits vorhanden:

- ATC-STD-MAINT-019 — Maintenance Evidence Standard
- ATC-STD-MAINT-000 — Maintenance Governance & Specification Standard
- ATC-STD-STD-003 — Governance Determinism & Source-of-Truth Matrix
- bestehende GitHub Actions / CI-Evidence in den Repositories

MAINT-019 ist damit die bestehende SSOT-Basis. Es wird kein paralleler,
unabhängiger Evidence-Standard vorgeschlagen.

## 3. Normative Change Proposal

ATC-STD-MAINT-019 soll um einen Workflow-Job-Evidence-Layer ergänzt werden.

### 3.1 Evidence hierarchy

\`Workflow → Run → Job → Step → Result → Finding → Contract → RCA → Fix → Commit → Rerun → Verification\`

Die Ebenen sind nicht austauschbar.

### 3.2 Workflow record

Pflichtfelder:

- workflow
- workflow_id oder workflow_file
- repository
- trigger
- pull_request / branch, sofern anwendbar
- expected_sha
- run.id
- run.status
- run.tested_sha
- run.exact_sha
- run.evidence_status

### 3.3 Job record

Pflichtfelder:

- job.id
- job.name
- job.result
- job.exit_code
- runner
- steps

Jeder relevante Step muss mindestens Name, Result und bei Fehlern die
technische Fehlermeldung referenzierbar machen.

### 3.4 Finding record

Ein technischer Befund MUSS von der CI-Meldung bis zur Architekturwirkung
nachvollziehbar sein.

Pflichtfelder:

- finding.id
- component
- file
- line oder lines, sofern verfügbar
- symbol, sofern verfügbar
- class
- tool/compiler error
- root_cause
- contract_impact
- status

### 3.5 Architecture contract

Jeder P0/P1-relevante Befund MUSS, sofern ein Architekturvertrag betroffen
ist, folgende Informationen enthalten:

- ssot
- expected_contract
- actual_implementation
- violation
- severity

Damit bleibt Architektur ≠ Implementierung ≠ Evidence.

### 3.6 Remediation

Ein behobener Befund MUSS nachvollziehbar sein über:

- minimal_fix
- commit
- changed_files
- validation

Gate-Umgehungen, Allowlist-Erweiterungen, Warnungsunterdrückung und
kosmetische "touch"-Commits gelten nicht als gültige Remediation.

### 3.7 Rerun / Verification

Ein Fix ist erst durch einen neuen Nachweis abgeschlossen.

Pflichtkette:

\`FIXED → RERUNNING → EXACT-SHA RUN → VERIFIED | RESIDUAL\`

Ein früherer PASS-Lauf darf keinen späteren Commit verifizieren.

## 4. Exact-SHA Contract

Für Evidence mit dem Status VERIFIED MUSS der getestete SHA eindeutig mit
dem zu verifizierenden Commit übereinstimmen.

Insbesondere gilt:

- PR merge refs sind nicht automatisch Exact-SHA Evidence.
- \`refs/pull/<n>/merge\` darf nicht als Nachweis für den PR-Head gewertet
  werden.
- Ein Run auf einem Merge-Commit darf nur als Evidence für genau diesen
  Merge-Commit verwendet werden.
- Ein PR-Head benötigt einen Nachweis, der den tatsächlichen PR-Head-SHA
  testet.
- Der getestete SHA MUSS im Job-/Run-Evidence eindeutig dokumentiert werden.

## 5. Evidence Status

Verbindliche Statuswerte:

- UNANALYZED
- ANALYZED
- FIXED
- RERUNNING
- VERIFIED
- RESIDUAL

\`VERIFIED\` ist ausschließlich zulässig, wenn alle für den Scope
erforderlichen Gates PASS sind und Exact-SHA-Bindung nachgewiesen wurde.

## 7. Traceability

Die normative Traceability-Kette lautet:

\`Source → Contract → Build/Test → Failure → RCA → Minimal Fix → Commit → Exact-SHA Rerun → Verification\`

Ein CI-Ergebnis ohne SHA-Bindung ist ein technisches Ergebnis, aber kein
vollständiger VERIFIED-Evidence-Nachweis.

## 8. Implementation requirement

Die Änderung an MAINT-019 soll nach §30 von ATC-STD-000 ausschließlich über
diesen SCR-Prozess erfolgen.

Nach Freigabe sind mindestens erforderlich:

1. Erweiterung des MAINT-019-Standards.
2. Aktualisierung des zugehörigen maschinenlesbaren Evidence-Schemas.
3. Workflow-/Validator-Unterstützung zur Prüfung der Exact-SHA-Bindung.
4. Dokumentation der Evidence-Records im vorgesehenen Repository-Pfad.
5. Testfälle für Merge-Ref vs. Exact-SHA.
6. Ein realer CI-Nachweis, der die neue Prüfung selbst validiert.

Bis diese Implementierung nachgewiesen ist, bleibt der Status
SPECIFICATION_ONLY bzw. RESIDUAL. Die Architektur darf nicht als
IMPLEMENTED oder VERIFIED bezeichnet werden.

## 9. Concrete reference finding

Run \`36679315410\` in
\`A-TownChain-Okosystems/a-townchain-ecosystem\` dient als Referenzfall.

Der Lauf prüfte den Merge-Ref
\`refs/remotes/pull/82/merge\` mit SHA \`ae61083...\`.
Damit ist der Lauf Evidence für den getesteten Merge-Commit, aber kein
Exact-SHA-VERIFIED-Nachweis für den tatsächlichen PR-Head.

Die daraus abgeleiteten Findings bleiben bis zur tatsächlichen Behebung und
Exact-SHA-Rerun als RESIDUAL dokumentiert.

## 10. Non-goals

Dieses SCR:

- schwächt keine CI-Gates;
- ersetzt keine Architektur-SSOT;
- erklärt Source Presence nicht zu Implementation;
- erklärt einen alten PASS-Lauf nicht zum aktuellen Nachweis;
- ersetzt keine fachlichen Tests;
- führt keine neue parallele Evidence-Hierarchie neben MAINT-019 ein.

## 11. Acceptance criteria

Das SCR ist technisch vollständig umgesetzt, wenn:

- MAINT-019 den Workflow-Job-Layer normativ abbildet;
- das Evidence-Schema Workflow/Run/Job/Step/Finding/Contract/Remediation/
  Rerun modelliert;
- Exact-SHA maschinenprüfbar ist;
- Merge-Ref und PR-Head unterschieden werden;
- VERIFIED ohne Exact-SHA-Bindung unmöglich ist;
- mindestens ein negativer und ein positiver Validator-Test existiert;
- ein realer CI-Run die Prüfung nachweist.
