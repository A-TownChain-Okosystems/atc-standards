# SCR-0129 — Canonical AI Development Lifecycle: Existing-First + Architecture-to-Evidence Gates

| Feld | Wert |
|---|---|
| SCR-ID | SCR-0129 |
| Datum | 2026-09-29 |
| Status | PROPOSED |
| Affected Standards | ATC-STD-AI-DEV-001, ATC-STD-AI-DEV-003, ATC-STD-AI-DEV-005, ATC-STD-AI-DEV-008, ATC-STD-AI-DEV-010 |
| Scope | AI Development Lifecycle, Existing-First Discovery, completeness, registry/SSOT validation, implementation, verification, documentation |
| Change Type | AI Development Governance / Workflow hardening |
| Risk | R2 — cross-standard workflow contract |

## 1. Decision Requested

Make the following lifecycle canonical for AI software-development agents across all ATC repositories:

```text
0 EXISTING-FIRST DISCOVERY
1 REQUIREMENT
2 DEPENDENCY ANALYSIS
3 ARCHITECTURE / INTEGRATION
4 COMPLETENESS AUDIT
5 GAP CLOSURE
6 REGISTRY / CONTRACT VALIDATION
7 CODE VALIDATION
8 IMPLEMENTATION + VERIFICATION
8.5 EVIDENCE GATE
9 DOCUMENTATION / SSOT SYNCHRONIZATION
```

The agent MUST NOT jump directly from a request to implementation.

## 2. Gate 0 — EXISTING-FIRST

Before creating or materially changing a component, function, API, interface, registry definition, data model, or subsystem, the agent MUST perform an evidence-backed search across the applicable organization/repository scope: repositories, source code, registries, architecture records, interfaces/APIs, data models, tests, configuration, documentation, and dependencies.

The search MUST be semantic/function-oriented, not filename-only. It MUST consider name, function, interface, data model, responsibility, layer, registry identity, and dependencies.

The result MUST be classified as REUSE, EXTEND, CONSOLIDATE, ARCHITECTURE REVIEW, COMPLETE, IMPLEMENTATION GAP, or NEW COMPONENT.

A new component is permitted only after the search demonstrates that reuse, extension, or consolidation is not appropriate.


### 2.1 Mandatory classification matrix

The Gate-0 result MUST use exactly one primary disposition:

| Discovery result | Mandatory action |
|---|---|
| Exact component/function exists | REUSE |
| Function exists but is incomplete | EXTEND |
| Multiple implementations exist | CONSOLIDATE and determine canonical SSOT |
| Function exists in another repository/layer | ARCHITECTURE REVIEW |
| Only stub/skeleton exists | COMPLETE / IMPLEMENT |
| Only documentation/specification exists | IMPLEMENTATION GAP; documentation MUST NOT be treated as implementation |
| Only tests exist | IMPLEMENTATION GAP |
| No applicable implementation exists | NEW COMPONENT |

The agent MUST preserve the evidence supporting the classification. NEW COMPONENT without a preceding Gate-0 record is invalid.

## 3. Existing-First Is Not Filename Existence

The agent MUST distinguish:

```text
FOUND != IMPLEMENTED != TESTED != CI-VERIFIED != CANONICAL
```

A file, test, documentation entry, or registry record alone MUST NOT be treated as proof of implementation.

## 4. Requirement Contract

The agent MUST establish objective/scope, acceptance criteria, required behavior, non-goals, security constraints, affected repositories/layers, and required evidence.

## 5. Dependency and Architecture Contract

Before implementation the agent MUST determine required components/functions, APIs/interfaces, data inputs/outputs, dependency graph, ownership, layer placement, Source of Truth, control/data flow, security boundaries, and affected contracts.

A component MUST NOT be implemented in a convenient but architecturally incorrect layer.

## 6. Completeness and Gap Closure

The agent MUST audit components, functions, APIs/interfaces, data models, error handling, security controls, tests, integration tests, E2E coverage, CI gates, registry records, documentation, and operational/release gates. Missing elements MUST be classified and either added to the existing implementation or explicitly recorded as blockers/non-goals.

## 7. Registry / Contract Validation

Before completion the agent MUST validate naming, IDs, registry membership, ownership, layer assignment, SSOT, schema compliance, dependency declarations, architecture contracts, and cross-repository references. New canonical components MUST follow Registry-First and SCR governance.


### 7.1 Registry-before-implementation rule

For a new canonical component, function, interface, or subsystem, Registry/Contract validation MUST occur before implementation is treated as canonical. The implementation MUST NOT establish a competing identity, owner, layer, or SSOT by convention or by code placement. If registry allocation is required by the applicable standard, implementation is blocked until the registry/contract decision is resolved.

## 8. Code Validation and Implementation

The agent MUST validate type correctness, API compatibility, error handling, security boundaries, deterministic behavior where applicable, testability, contract compatibility, and dependency correctness.

Implementation MUST proceed through:

```text
CODE → BUILD → UNIT TEST → INTEGRATION TEST → E2E TEST
```

Failures MUST be fixed at root cause. Gate weakening, test deletion, cosmetic-only CI changes, and false status claims are prohibited.

## 9. Evidence Gate

A capability MUST NOT receive VERIFIED status without evidence. For critical changes:

```text
RUN → JOB → STEP → LOG → SOURCE → ROOT CAUSE → MINIMAL FIX → COMMIT → RERUN
```

Where CI evidence is required, it MUST correspond to the exact commit SHA being assessed. Local success MUST NOT be represented as Exact-SHA CI verification.

## 10. Status Model

```text
DISCOVERED → DESIGNED → REGISTERED → IMPLEMENTED → BUILT → UNIT-TESTED
→ INTEGRATION-TESTED → E2E-VERIFIED → CI-VERIFIED → DOCUMENTED
→ CANONICAL / RELEASE-READY
```

Explicitly invalid equivalences: file exists != IMPLEMENTED; documentation exists != IMPLEMENTED; local build passes != CI-VERIFIED; test exists != implementation verified; registry entry exists != implementation verified.

## 11. Function Contract

For every new or materially changed function the agent MUST establish purpose, reason for existence, existing equivalent, SSOT, owning layer/repository, API, inputs/outputs, error cases, security boundary, dependencies, required tests, registry impact, and documentation impact.

## 12. Component Contract

For every new or materially changed component the agent MUST establish existing implementation search result, duplicate/parallel implementation analysis, owner repository, owner layer, SSOT, interfaces, dependencies, security boundary, registry ID, tests, CI gates, actual implementation state, and exact-SHA verification state.

## 13. Change Propagation

Any contract-affecting change MUST trigger a consistency review across:

```text
Source → API → Registry → Dependencies → Tests → CI → Architecture → Documentation → E2E
```

Inconsistency blocks completion.

## 14. Governance and Human Authority

This SCR does not grant AI agents approval authority. Approved-standard changes remain SCR-governed; AI agents execute and provide evidence; human/governance approval remains required where mandated; no AI agent may silently redefine an approved SSOT.

## 15. Required Standard Updates After Approval

After approval, update the affected AI-DEV standards so the lifecycle is expressed once as the canonical workflow rather than duplicated inconsistently:

1. ATC-STD-AI-DEV-001 — make Gate 0 and the complete lifecycle normative.
2. ATC-STD-AI-DEV-003 — align Repository Discovery with Existing-First and semantic discovery.
3. ATC-STD-AI-DEV-005 — require discovery/classification evidence.
4. ATC-STD-AI-DEV-008 — align validation stages and Exact-SHA evidence.
5. ATC-STD-AI-DEV-010 — synchronize documentation only after verified state.

Generated registry/index/views MUST be regenerated from their SSOT; no hand-edited generated output.

## 16. Acceptance Criteria

1. Gate 0 is mandatory before implementation.
2. Existing functionality is searched semantically across the applicable scope.
3. Reuse/extend/consolidate/new decisions are recorded.
4. The lifecycle is represented consistently in the AI-DEV family.
5. Registry/SSOT/ownership/layer validation is mandatory.
6. Completeness checks include tests, security, CI and operational gates.
7. Exact-SHA CI evidence is required for VERIFIED status where CI is applicable.
8. Documentation cannot claim a higher state than technical evidence.
9. Contract changes trigger cross-repository consistency checks.
10. Validators/CI enforce the new mandatory gates where technically applicable.
11. No existing canonical implementation is duplicated without an explicit architecture decision.

## 17. Non-Goals

This SCR does not create a second AI-development governance family, replace ATC-STD-000, grant AI agents approval authority, redefine repository ownership, declare existing implementations verified without new evidence, or weaken existing CI/security gates.

## 18. Governance Note

ATC-STD-AI-DEV-001 is APPROVED and MUST NOT be silently rewritten. This SCR is the formal change basis. After approval, implementation SHALL proceed through controlled updates of affected standards, registry metadata, validators, and generated views.
