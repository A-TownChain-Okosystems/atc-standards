## 1. Zweck

Dieser SCR schlägt einen verbindlichen Architekturvertrag für das A-TownChain-Ökosystem vor:

> **Standalone First, Ecosystem Second.**

Jede Kernkomponente MUSS außerhalb des Umbrella-Repositories eigenständig nutzbar, buildbar und testbar sein. Das Repository `a-townchain-ecosystem` ist Integrations-, Kompatibilitäts- und Systemverifikationsebene und darf nicht zum fachlichen Source-of-Truth einer Kernkomponente werden.

## 2. Architektur-Invariante

Die Standalone-Fähigkeit einer Kernkomponente darf durch ihre Ecosystem-Integration nicht verloren gehen.

Verbindliche Ownership-Regel:

**Source Repository owns the component.**

**Ecosystem Repository verifies the composition.**

Das Ecosystem darf Quell-Repositories integrieren und verifizieren, aber keine fachliche Implementierung aus dem Source Repository in eine zweite, konkurrierende SSOT überführen.

## 3. Geltungsbereich

Der Contract gilt für die Kernsysteme:

- ShivaCore — Kernel/TCB
- GlobusOS — Betriebssystem
- ATCLang — Sprache/Toolchain
- ATC-VM — Execution Runtime
- A-TownChain — L1 Blockchain
- Aurora AI — AI/Agent Platform
- Genesis Engine — Application/Game Engine

Weitere Repository-Klassen können den Contract übernehmen; die Conformance-Anforderungen werden dabei anhand des Repository-Profils aus `registry/repositories.yaml` konkretisiert.

## 4. Standalone Conformance

Standalone Conformance besteht aus G01–G06:

| Gate | Pflichtnachweis |
|---|---|
| G01 | Standalone Build — Build ohne `a-townchain-ecosystem` |
| G02 | Standalone Tests — eigene Test-Suite unabhängig ausführbar |
| G03 | Dependency Boundary — Abhängigkeiten explizit, minimal und nachvollziehbar |
| G04 | Public API/ABI — definierte externe Schnittstellen |
| G05 | No Umbrella Dependency — keine fachliche Abhängigkeit vom Umbrella-Repository |
| G06 | Documentation — Installation, Nutzung, Architektur und externe Schnittstellen dokumentiert |

Ein Repository mit einem fehlenden oder fehlgeschlagenen Pflicht-Gate ist **Standalone Conformance = FAIL**.

## 5. Ecosystem Conformance

Ecosystem Conformance besteht aus G07–G08:

| Gate | Pflichtnachweis |
|---|---|
| G07 | Ecosystem Integration — definierte Integration in den Gesamtstack funktioniert |
| G08 | Cross-System E2E — systemübergreifender, reproduzierbarer End-to-End-Nachweis |

Ecosystem Conformance setzt Standalone Conformance voraus.

Formal:

`StandaloneConformance = PASS AND EcosystemConformance = PASS`

ist Voraussetzung für eine Ecosystem-Release-Freigabe.

Ein grüner G08-Nachweis darf einen fehlenden oder fehlerhaften G01–G06-Nachweis **nicht kompensieren**.

## 6. Dependency Direction

Zulässige Richtung:

```
                 a-townchain-ecosystem
                 Integration / Evidence
                           |
          +----------------+----------------+
          |                |                |
          v                v                v
     ShivaCore        A-TownChain       Aurora AI
     Standalone       Standalone        Standalone
          |                |                |
          +----------------+----------------+
                           |
                    Cross-System E2E
```

Unzulässig ist eine Architektur, in der eine Kernkomponente fachlich vom Umbrella-Repository abhängt, sodass sie außerhalb des Ecosystems nicht mehr eigenständig gebaut oder betrieben werden kann.

## 7. Release Contract

Ein Component Release MUSS Standalone Conformance getrennt von Ecosystem Compatibility ausweisen.

```
Component Release
├── Standalone Conformance
│   └── eigenständig verwendbar
└── Ecosystem Compatibility
    └── kompatibel mit definierter Ecosystem-Version
```

Unabhängige Release-Zyklen sind zulässig. Ein neues Release einer Komponente erzwingt nicht automatisch ein Release jeder anderen Komponente.

## 8. Evidence

Jedes Conformance-Gate MUSS maschinenlesbare Evidence liefern, insbesondere:

- Repository und Commit SHA
- Workflow/Job/Step
- Test-/Build-Ergebnis
- verwendete Versionen und relevante Dependency-Locks
- Zeitpunkt
- Gate-ID
- PASS/FAIL
- bei FAIL: reproduzierbare Fehlerursache

Evidence ist dem jeweiligen Source Repository für G01–G06 zuzuordnen. G07–G08 werden zusätzlich im Ecosystem-Kontext nachgewiesen.

## 9. CI-Enforcement

Für Kern-Repositories sollen Standalone-Gates als eigene CI-Gates eingeführt werden:

```
Standalone Conformance
├── G01 Build
├── G02 Tests
├── G03 Dependency Boundary
├── G04 API/ABI
├── G05 No Umbrella Dependency
└── G06 Documentation
```

Im Umbrella:

```
Ecosystem Conformance
├── G07 Integration
├── G08 Cross-System E2E
└── Evidence / Governance
```

Die CI MUSS bei Standalone FAIL die Ecosystem-Release-Freigabe blockieren.

## 10. SSOT und Governance

`atc-standards` bleibt normative SSOT.

Das jeweilige Source Repository bleibt fachliche SSOT seiner Komponente.

`a-townchain-ecosystem` bleibt Integrations- und Verifikationsschicht.

Standards, Registry-Einträge und normative Änderungen erfolgen gemäß ATC-STD-000 über SCR und §9-Freigabe. Der Umbrella darf den Standard nicht duplizieren; er soll nach APPROVED-Freigabe lediglich darauf referenzieren und seine Conformance-Evidence liefern.

## 12. Acceptance Criteria

1. `ATC-STD-ARCH-001` ist nach §9 als APPROVED freigegeben oder der SCR bleibt PROPOSED.
2. Der Standard ist in `registry/standards.yaml` und den erforderlichen registry-derived Artefakten registriert.
3. Die Kern-Repositories besitzen einen Standalone-Conformance-Nachweis G01–G06.
4. `a-townchain-ecosystem` besitzt G07–G08.
5. Standalone FAIL blockiert Ecosystem Release Readiness.
6. Keine Kernkomponente benötigt fachliche Imports aus `a-townchain-ecosystem`.
7. Component Releases und Ecosystem Compatibility sind getrennt nachvollziehbar.
8. Evidence ist commit- und workflowbezogen reproduzierbar.

## 13. Abgrenzung

Dieser SCR ändert keine Konsensregeln, Tokenomics, VM-Gas-Regeln, Kryptographie oder Laufzeitsemantik. Er definiert ausschließlich Architektur-, Ownership-, Dependency-, Release- und Conformance-Regeln.
