# SCR-0129 — Workflow Job Evidence Architecture & Exact-SHA Verification

## 1. Purpose

Dieses SCR erweitert die bestehende Evidence-Governance um ein verbindliches,
workflow- und jobbezogenes Evidence-Modell.

Ein GitHub Actions Workflow-Job darf nicht nur als PASS/FAIL-Signal betrachtet
werden. Der Job ist ein prüfbares Evidence-Objekt mit reproduzierbarer
Zuordnung zu Workflow, Run, Job, getesteter Revision, Steps, technischen
Findings, Architekturvertrag, Root Cause, Minimal Fix und Rerun.

Der bestehende ATC-Standard MAINT-019 definiert bereits ein allgemeines
maschinenlesbares Evidence-Modell, ist aktuell jedoch ausdrücklich
SPECIFICATION_ONLY. Dieses SCR konkretisiert die Workflow-/Job-Ebene und
definiert die Exact-SHA-Anforderung.

## 2. Existing-First Finding

Bereits vorhanden:

- ATC-STD-MAINT-019 — Maintenance Evidence Standard
- ATC-STD-MAINT-000 — Maintenance Governance & Specification Standard
- ATC-STD-STD-003 — Governance Determinism & Source-of-Truth Matrix
- bestehende GitHub Actions / CI-Evidence in den Repositories

MAINT-019 ist damit die bestehende SSOT-Basis. Es wird kein paralleler,
unabhängiger Evidence-Standard vorgeschlagen.

## 3. Normative Change Proposal

ATC-STD-MAINT-019 soll um einen Workflow-Job-Evidence-Layer ergänzt werden.

### 3.1 Evidence hierarchy

\`Workflow → Run → Job → Step → Result → Finding → Contract → RCA → Fix → Commit → Rerun → Verification\`

Die Ebenen sind nicht austauschbar.

### 3.2 Workflow record

Pflichtfelder:

- workflow
- workflow_id oder workflow_file
- repository
- trigger
- pull_request / branch, sofern anwendbar
- expected_sha
- run.id
- run.status
- run.tested_sha
- run.exact_sha
- run.evidence_status

### 3.3 Job record

Pflichtfelder:

- job.id
- job.name
- job.result
- job.exit_code
- runner
- steps

Jeder relevante Step muss mindestens Name, Result und bei Fehlern die
technische Fehlermeldung referenzierbar machen.

### 3.4 Finding record

Ein technischer Befund MUSS von der CI-Meldung bis zur Architekturwirkung
nachvollziehbar sein.

Pflichtfelder:

- finding.id
- component
- file
- line oder lines, sofern verfügbar
- symbol, sofern verfügbar
- class
- tool/compiler error
- root_cause
- contract_impact
- status

### 3.5 Architecture contract

Jeder P0/P1-relevante Befund MUSS, sofern ein Architekturvertrag betroffen
ist, folgende Informationen enthalten:

- ssot
- expected_contract
- actual_implementation
- violation
- severity

Damit bleibt Architektur ≠ Implementierung ≠ Evidence.

### 3.6 Remediation

Ein behobener Befund MUSS nachvollziehbar sein über:

- minimal_fix
- commit
- changed_files
- validation

Gate-Umgehungen, Allowlist-Erweiterungen, Warnungsunterdrückung und
kosmetische "touch"-Commits gelten nicht als gültige Remediation.

### 3.7 Rerun / Verification

Ein Fix ist erst durch einen neuen Nachweis abgeschlossen.

Pflichtkette:

\`FIXED → RERUNNING → EXACT-SHA RUN → VERIFIED | RESIDUAL\`

Ein früherer PASS-Lauf darf keinen späteren Commit verifizieren.

## 4. Exact-SHA Contract

Für Evidence mit dem Status VERIFIED MUSS der getestete SHA eindeutig mit
dem zu verifizierenden Commit übereinstimmen.

Insbesondere gilt:

- PR merge refs sind nicht automatisch Exact-SHA Evidence.
- \`refs/pull/<n>/merge\` darf nicht als Nachweis für den PR-Head gewertet
  werden.
- Ein Run auf einem Merge-Commit darf nur als Evidence für genau diesen
  Merge-Commit verwendet werden.
- Ein PR-Head benötigt einen Nachweis, der den tatsächlichen PR-Head-SHA
  testet.
- Der getestete SHA MUSS im Job-/Run-Evidence eindeutig dokumentiert werden.

## 5. Evidence Status

Verbindliche Statuswerte:

- UNANALYZED
- ANALYZED
- FIXED
- RERUNNING
- VERIFIED
- RESIDUAL

\`VERIFIED\` ist ausschließlich zulässig, wenn alle für den Scope
erforderlichen Gates PASS sind und Exact-SHA-Bindung nachgewiesen wurde.

## 7. Traceability

Die normative Traceability-Kette lautet:

\`Source → Contract → Build/Test → Failure → RCA → Minimal Fix → Commit → Exact-SHA Rerun → Verification\`

Ein CI-Ergebnis ohne SHA-Bindung ist ein technisches Ergebnis, aber kein
vollständiger VERIFIED-Evidence-Nachweis.

## 8. Implementation requirement

Die Änderung an MAINT-019 soll nach §30 von ATC-STD-000 ausschließlich über
diesen SCR-Prozess erfolgen.

Nach Freigabe sind mindestens erforderlich:

1. Erweiterung des MAINT-019-Standards.
2. Aktualisierung des zugehörigen maschinenlesbaren Evidence-Schemas.
3. Workflow-/Validator-Unterstützung zur Prüfung der Exact-SHA-Bindung.
4. Dokumentation der Evidence-Records im vorgesehenen Repository-Pfad.
5. Testfälle für Merge-Ref vs. Exact-SHA.
6. Ein realer CI-Nachweis, der die neue Prüfung selbst validiert.

Die Implementierung ist auf dem SCR-Branch vorhanden. Sie ist noch nicht auf `main` wirksam und darf bis zur vorgesehenen Review-/Freigabephase nicht als mainline-VERIFIED bezeichnet werden.

## 9. Implementation evidence

Implementiert auf `feat/scr-0129-workflow-job-evidence`:

- `schemas/maintenance/workflow-evidence.schema.json`
- `tools/maintenance/validate_workflow_evidence.py`
- `tools/maintenance/tests/test_workflow_evidence.py`
- CI-Step `Workflow Evidence Validator` in `.github/workflows/maintenance-conformance.yml`
- Self-test fixture `.github/workflows/workflow-evidence-self-test.json`
- MAINT-019 Workflow-/Job-Evidence-Layer mit fail-closed Exact-SHA-Regeln

Validator-Tests umfassen mindestens:

1. PR-Merge-Ref → FAIL.
2. `tested_sha != expected_sha` → FAIL.
3. identischer SHA auf Nicht-Merge-Ref → PASS.
4. `VERIFIED` ohne `exact_sha=true` → FAIL.

Der reale GitHub-Actions-Lauf des Implementierungs-Branches ist der noch ausstehende Evidence-Schritt; erst dieser Lauf kann die CI-Verdrahtung selbst als real ausgefuehrt nachweisen.

## 10. Concrete reference finding

Run \`36679315410\` in
\`A-TownChain-Okosystems/a-townchain-ecosystem\` dient als Referenzfall.

Der Lauf prüfte den Merge-Ref
\`refs/remotes/pull/82/merge\` mit SHA \`ae61083...\`.
Damit ist der Lauf Evidence für den getesteten Merge-Commit, aber kein
Exact-SHA-VERIFIED-Nachweis für den tatsächlichen PR-Head.

Die daraus abgeleiteten Findings bleiben bis zur tatsächlichen Behebung und
Exact-SHA-Rerun als RESIDUAL dokumentiert.

## 11. Non-goals

Dieses SCR:

- schwächt keine CI-Gates;
- ersetzt keine Architektur-SSOT;
- erklärt Source Presence nicht zu Implementation;
- erklärt einen alten PASS-Lauf nicht zum aktuellen Nachweis;
- ersetzt keine fachlichen Tests;
- führt keine neue parallele Evidence-Hierarchie neben MAINT-019 ein.

## 12. Acceptance criteria

Das SCR ist technisch vollständig umgesetzt, wenn:

- MAINT-019 den Workflow-Job-Layer normativ abbildet;
- das Evidence-Schema Workflow/Run/Job/Step/Finding/Contract/Remediation/
  Rerun modelliert;
- Exact-SHA maschinenprüfbar ist;
- Merge-Ref und PR-Head unterschieden werden;
- VERIFIED ohne Exact-SHA-Bindung unmöglich ist;
- mindestens ein negativer und ein positiver Validator-Test existiert;
- ein realer CI-Run die Prüfung nachweist.


## Workflow Job Log Architecture (normative evidence interpretation)

Workflow-Job-Logs sind kein unstrukturierter Debug-Anhang, sondern die niedrigste technische Evidence-Schicht innerhalb der Workflow-Evidence-Kette. Sie liefern die beobachtbaren Fakten fuer Run → Job → Step → Result/Exit Code und muessen fuer Findings bis zur konkreten Quelle zurueckverfolgbar sein.

### Log-Evidence-Kette

```
Workflow
  ↓
Run
  ↓
Job
  ↓
Step
  ↓
Command / Action
  ↓
Observed Output
  ↓
Exit Code / Conclusion
  ↓
Finding
  ↓
Source / Contract
  ↓
Root Cause
  ↓
Minimal Fix
  ↓
Commit
  ↓
Exact-SHA Rerun
  ↓
VERIFIED | RESIDUAL
```

### Required Log Record

Ein archiviertes Workflow-Job-Evidence-Record MUSS mindestens folgende Referenzen erhalten, sofern vom Provider verfuegbar:

| Feld | Bedeutung |
|---|---|
| workflow | Kanonischer Workflowname/-ID |
| run_id | Eindeutige GitHub-Actions-Run-ID |
| job_id | Eindeutige Job-ID |
| job_name | Technischer Jobname |
| checkout_ref | Tatsächlich getestete Git-Ref |
| tested_sha | Tatsächlich ausgecheckter Commit |
| exact_sha | Ergebnis der SHA-Bindungspruefung |
| step | Fehlender/erfolgreicher Ausfuehrungsschritt |
| command/action | Ausgefuehrtes Tool oder Action |
| result | Step-/Job-Ergebnis |
| exit_code | Prozess-Exit-Code, sofern vorhanden |
| log_excerpt | Minimale relevante Logstelle |
| source | Datei/Symbol/Contract-Quelle |
| finding_id | Verknuepfte Finding-ID |

### Reference Case: Run 36679315410 / Job 109771084299

Der reale Job-Log liefert die Architektur-Evidence unmittelbar:

- Workflow-Run: `36679315410`
- Job: `rust-manifests` / `109771084299`
- Job-Ergebnis: FAILURE
- Fehlernder Step: `Validate every Rust workspace/package once`
- Checkout-Ref: `refs/remotes/pull/82/merge`
- getesteter SHA: `ae61083bf28407452d7621dc0c64feb80a7c5557`
- Exit Code: `1`
- Rust: `1.98.1`
- Runner: Ubuntu 24.04.5 / `ubuntu-24.04`

Der Log zeigt damit nicht nur, dass CI rot ist, sondern die komplette technische Kette bis zur Quelle. Beispiele:

1. `blockchain.rs:1686`: `CaptureTransport` implementiert `PeerTransport` nicht vollständig; `send_to` fehlt.
2. `mempool.rs:698`: `MAX_ATC_SUPPLY:u128` wird an `genesis_credit(..., n:u64)` übergeben — Monetary-Type-Contract verletzt.
3. `storage.rs:1169` und `1224`: Tests referenzieren `recover_state_with_dao()`, die aktuelle Implementierung bietet `recover_state()` — API/Test-Contract muss Existing-First geklaert werden.
4. `storage.rs:411` und `443`: Borrow-Lifetime E0716 durch temporären Read-Lock.
5. `mempool.rs:2` und `693`: ungenutzte Economics-Imports unter `-D warnings`.
6. `components/a-townchain/components/algorithm/src/lib.rs:10`: rustfmt-Differenz.

### Architectural Interpretation

Der Log darf nicht selbst den Root Cause erfinden. Er ist die Evidence-Quelle fuer die beobachtete Abweichung. Die RCA muss den Log-Befund mit SSOT, Contract und Source korrelieren.

Damit gilt verbindlich:

`Log ≠ RCA`

`Log → Finding → SSOT/Contract → RCA → Minimal Fix`

Ein erfolgreicher Log ist ebenfalls nur Evidence fuer den konkret getesteten SHA und die konkret ausgefuehrten Gates. Ein alter PASS darf keinen spaeteren Commit verifizieren.

### Exact-SHA consequence

Da Job 109771084299 explizit `refs/remotes/pull/82/merge` auscheckt, ist dieser Log ein valider Failure-Nachweis fuer den getesteten Merge-Commit, aber **kein Exact-SHA-Nachweis fuer den PR-Head**. Genau diese Unterscheidung ist Bestandteil des SCR-0129-Validators.
