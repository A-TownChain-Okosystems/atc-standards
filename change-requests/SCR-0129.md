## 1. Zweck der Änderung

Das SCR-Modell soll nicht nur dokumentieren, **was** geändert wird, sondern vor einer Umsetzung belastbar beantworten:

1. Wofür ist die Änderung gut?
2. Ist die Änderung erforderlich?
3. Warum ist die Änderung erforderlich?
4. Verbessert die Änderung das System?
5. Ist die Änderung sicher?
6. Was muss gemacht werden, damit die Änderung vollständig umgesetzt ist?

Ziel ist eine vollständige Decision- und Evidence-Kette von der Änderungsabsicht bis zur verifizierten Systemänderung.

## 2. Ist-Zustand

ATC-STD-CHANGE-001 verlangt bereits eine SCR-Kanal-Pflicht, Gate-Landkarte, RACI, Traceability und 13 Change-Nachweis-Fragen. Diese decken WHAT/WHY, Verantwortlichkeit, Version, Standard, Requirement, Dependencies, Tests, Dokumentation, Security, Compatibility und Audit Evidence ab.

Die zusätzliche Governance-Lücke besteht darin, dass **Nutzen, Erforderlichkeit, systemische Verbesserung, Safety/Security und vollständige Umsetzung** nicht als eigene, explizite Gates strukturiert sind.

Insbesondere gilt:

- IMPLEMENTED ist nicht gleich VERIFIED.
- CI PASS ist nicht automatisch Verification Evidence.
- Error Evidence ist nicht Finding Evidence.
- Finding Evidence ist nicht Verification Evidence.
- Ein vorhandener Commit beweist nicht die vollständige Umsetzung.
- Eine behauptete Verbesserung benötigt nachvollziehbare Before/After-Evidence.

## 3. Zielmodell

Jeder SCR MUSS künftig folgende Entscheidungs- und Nachweisbereiche enthalten:

### 3.1 Purpose — Wofür ist die Änderung gut?

Pflichtfelder:

- Objective
- Problem solved
- System benefit
- User/consumer benefit, falls relevant
- Technical/operational benefit, falls relevant
- Expected measurable outcome, falls messbar

### 3.2 Necessity — Ist die Änderung erforderlich?

Pflichtfelder:

- required: true|false
- Classification: MANDATORY | REQUIRED | CONDITIONAL | OPTIONAL | REJECTED
- Requirement source
- Blocking consequence, falls nicht umgesetzt
- Affected invariants
- Reason for necessity

Eine optionale Verbesserung DARF nicht als zwingende Systemanforderung klassifiziert werden.

### 3.3 Rationale — Warum ist die Änderung erforderlich?

Pflichtfelder:

- Why
- Why now
- Root cause
- Requirement / contract reference
- Consequence without change
- Technical rationale

Kanonische Kette:

Requirement → Problem → Root Cause → Consequence → Required Change

### 3.4 Improvement — Verbessert die Änderung das System?

Der SCR MUSS Before/After und die tatsächlich betroffenen Dimensionen dokumentieren.

Bewertungsdimensionen:

- Correctness
- Security
- Reliability
- Performance
- Maintainability
- Interoperability
- Determinism
- Observability
- Operability
- Compatibility

Nur nachgewiesene Verbesserungen dürfen als Verbesserung behauptet werden. Nicht betroffene Dimensionen sind N/A, nicht künstlich PASS.

### 3.5 Safety & Security — Ist die Änderung sicher?

Pflichtprüfung mindestens für:

- Security impact
- Safety impact, falls relevant
- Attack-surface change
- Authorization / capability impact
- Cryptography impact
- Secrets / credentials impact
- Data integrity
- Availability / reliability
- Compatibility / breaking change
- New failure modes
- Rollback / recovery
- Residual risk

Regel:

> safe: true ohne zugehörige Evidence ist kein gültiger Safety-/Security-Nachweis.

### 3.6 Completeness — Was muss gemacht werden, damit die Änderung vollständig umgesetzt ist?

Jeder SCR MUSS eine Completion Matrix enthalten:

| Bereich | Required | Status | Evidence |
|---|---:|---|---|
| Architecture / SSOT | YES/NO | OPEN/DONE/N/A | Referenz |
| Specification / Contract | YES/NO | OPEN/DONE/N/A | Referenz |
| Source Code | YES/NO | OPEN/DONE/N/A | Commit |
| API | YES/NO | OPEN/DONE/N/A | Tests/Evidence |
| ABI / Wire Format | YES/NO | OPEN/DONE/N/A | Tests/Evidence |
| State / Storage | YES/NO | OPEN/DONE/N/A | Tests/Evidence |
| Security | YES/NO | OPEN/DONE/N/A | Security Evidence |
| Tests | YES/NO | OPEN/DONE/N/A | Test Evidence |
| Integration | YES/NO | OPEN/DONE/N/A | Integration Evidence |
| CI/CD | YES/NO | OPEN/DONE/N/A | Exact-SHA Evidence |
| Documentation | YES/NO | OPEN/DONE/N/A | Commit |
| Migration | YES/NO | OPEN/DONE/N/A | Migration Evidence |
| Compatibility | YES/NO | OPEN/DONE/N/A | COMPAT Evidence |
| Release | YES/NO | OPEN/DONE/N/A | Release Evidence |
| Audit | YES/NO | OPEN/DONE/N/A | AUD Evidence |

CLOSED/VERIFIED ist nur zulässig, wenn alle erforderlichen Punkte DONE oder begründet N/A sind.

## 4. Evidence Separation

Die bestehende Evidence-Architektur wird explizit erweitert:

Architecture / SSOT / Contract
→ Change
→ Error Evidence
→ Finding Evidence
→ Root Cause
→ Minimal Fix
→ Implementation
→ Exact-SHA Verification
→ Verification Evidence
→ Completeness
→ Closure

Normative Trennung:

> **Error Evidence ≠ Finding Evidence ≠ Verification Evidence**

Ein Log darf daher nicht gleichzeitig als Root-Cause-, Fix- und Verification-Nachweis behandelt werden.

## 5. Status- und Closure-Regeln

Die SCR-State-Machine wird um explizite Entscheidungs- und Vollständigkeitszustände geführt:

UNANALYZED → ANALYZED → PLANNED → IMPLEMENTING → FIXED → RERUNNING → VERIFIED → CLOSED

Zusätzliche terminale/alternative Zustände:

- REJECTED
- FAILED
- RESIDUAL

Pflichtregeln:

- FIXED ≠ VERIFIED
- PASS ≠ VERIFIED
- IMPLEMENTED ≠ COMPLETE
- VERIFIED ohne Exact-SHA-Evidence ist bei CI-relevanten Änderungen ungültig.
- CLOSED ohne Completion Assessment ist ungültig.

## 6. Normative SCR-Pflichtfragen

Zusätzlich zu den bestehenden 13 Change-Nachweis-Fragen MUSS jeder SCR beantworten:

1. What is being changed?
2. What is the purpose of the change?
3. What problem does it solve?
4. Is the change required?
5. Why is it required?
6. Why now?
7. What happens if it is not implemented?
8. Does the change improve the system?
9. Which system dimensions improve?
10. What evidence demonstrates the improvement?
11. Is the change safe and secure?
12. What risks and new failure modes exist?
13. What residual risks remain?
14. What exactly must be completed for the change to be complete?
15. Which components, interfaces, tests, documentation, migrations and release artifacts are affected?
16. What evidence is required before closure?

Diese Fragen ergänzen die bestehenden Traceability-Fragen; sie ersetzen sie nicht.

## 7. Acceptance / Closure Gate

Ein SCR darf erst geschlossen werden, wenn:

- Existing-First durchgeführt wurde
- SSOT identifiziert wurde
- Purpose dokumentiert wurde
- Necessity klassifiziert und begründet wurde
- Rationale dokumentiert wurde
- Impact analysiert wurde
- Improvement Before/After beschrieben wurde
- Safety/Security bewertet wurde
- Root Cause dokumentiert wurde, falls ein Finding vorliegt
- Minimal Fix definiert und umgesetzt wurde
- Implementation commitbar und traceable ist
- erforderliche Tests ausgeführt wurden
- Exact-SHA-Verifikation vorliegt, sofern CI relevant
- Error/Finding/Verification Evidence getrennt vorliegen
- Completion Matrix vollständig ist
- Documentation/SSOT synchronisiert ist
- Residual Risks bewertet sind
- Audit-/Human-Gates erfüllt sind

## 8. Abgrenzung

SCR-0129 ändert keine Protokoll-, Konsens-, VM-, Crypto- oder Runtime-Semantik.

Die Änderung betrifft ausschließlich die Governance- und Evidence-Schicht des Change-Control-Prozesses.

ATC-STD-CHANGE-001 bleibt die Dachnorm; ATC-STD-999 bleibt die Master-Audit-Instanz. Es wird keine parallele Change-Control-Struktur eingeführt.

## 10. Success Criteria

SCR-0129 gilt als umgesetzt, wenn:

1. die erweiterten Pflichtfelder normativ definiert sind;
2. Purpose, Necessity, Rationale, Improvement, Safety und Completeness maschinen-/menschenprüfbar sind;
3. Error/Finding/Verification Evidence getrennt bleiben;
4. CLOSED ohne vollständige Completion Matrix verhindert wird;
5. Exact-SHA-Verifikation bei CI-relevanten Änderungen verbindlich ist;
6. mindestens ein SCR erfolgreich gegen das erweiterte Modell validiert wurde;
7. Registry, Index und Dokumentation synchron sind;
8. die Änderung selbst durch unabhängige Verification Evidence nachgewiesen ist.

## 11. Governance Decision

**Vorgeschlagene Entscheidung:** APPROVE als additive Erweiterung des SCR-Change-Control-Modells.

**Normative Umsetzung:** erst nach Owner-/§9-Freigabe und erfolgreicher Validator-/CI-Verifikation.

**Closure:** nicht durch diesen Vorschlag selbst. SCR-0129 bleibt bis zur vollständigen Umsetzung und Verification PROPOSED bzw. anschließend im jeweiligen Implementierungsstatus.
