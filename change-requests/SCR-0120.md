## 2. Kanonisierte Kernprinzipien (Owner-Direktive)

1. **Vier Maintenance-Klassen verbindlich** mit Beispielen, SLAs und Regeln: M2 darf normalen Release-Zyklen vorgelagert werden; M3 (Konsensfehler, Kernel Security Boundary, VM-Inkompatibilitaet, Chain-State-Korruption, Datenverlust, kritische RCE, kryptografischer Vertrauensbruch) folgt dem Emergency-Pfad und kann normale Governance-Zyklen uebersteuern.
2. **Einheitlicher 13-Phasen-Lifecycle** — Maintenance ist kein paralleles Chaos-System, sondern spezialisierter Lifecycle innerhalb der bestehenden GSEPF-Engineering-Governance.
3. **Maintenance Evidence** (MAINT-019): verbindliches maschinenlesbares Record-Schema (id MAINT-YYYY-NNNN, classification, change before/after, validation unit/integration/security/compatibility/performance, rollback available/tested, evidence commit/PR/test_report/audit_report, status) — „No Evidence, No Trust"; „Update durchgefuehrt" ist KEIN gueltiger Abschluss.
4. **Maintenance Gates + Separation of Duties**: M0 Standard Review, M1 Operational Review, M2 Security Review, M3 Emergency Governance; fuer M2/M3: Implementer ≠ Validator ≠ Auditor; bei besonders kritischen Aenderungen Release Authority ≠ Implementer.
5. **KAI-OS-harte Maintenance-Grenzen**: Schichtgrenzen (Aurora/GlobusOS/ShivaCore/ATC-VM/A-TownChain/ATCLang/Hardware) sind Maintenance-Grenzen; ein ATC-VM-Update ist niemals ein normales Dependency-Update und prueft mindestens die 7-Stufen-Kette (MAINT-009 §1).
6. **Verbindliche KPIs**: MTTA, MTTD, MTTR, MTBF, Patch Latency, Dependency Freshness, Technical Debt, Maintenance Backlog, Rollback Success Rate, Regression Rate, Evidence Completeness, Recovery Readiness — generiert, nie handgezahlt.
7. **Repository-Level Requirement**: kritische Repositories erhalten MAINTENANCE.md + docs/maintenance/; kleinere Repos einen README-Maintenance-Abschnitt.
8. **Automatisierung (MAINT-020)**: Repository-Scanner → Maintenance Engine → M0 Auto / M1 Review / M2-M3 Escalate; keine autonome M2/M3-Durchfuehrung.
9. **Maintenance-Readiness-Gate (v3, MAINT-000 §3)**: „Maintenance ist kein Post-Release-Prozess. Maintenance Capability ist eine Release-Voraussetzung." — kein Release ohne vollstaendige maintenance_readiness (maintenance_owner, maintenance_documentation, dependency_inventory, security_process, test_suite, rollback_strategy, compatibility_strategy, monitoring, evidence_collection, lifecycle_status); M2/M3-Releases zusaetzlich critical_maintenance (independent_validation, security_review, rollback_test, incident_record, audit_evidence). BLOCK bei NO.
10. **Prioritaeten KAI-OS (v3, verbindlich)**: P0 unverzichtbar: 000, 001, 002, 004, 005, 007, 008, 009, 015, 017, 018, 019. P1 produktionsrelevant: 003, 006, 010, 011, 012, 014, 016, 020, 021. P2 Ecosystem Maturity: 013, 022, 023, 024.
11. **Zielarchitektur (v3, MAINT-000 §2 / MAINT-020 §4)**: ATC-STD-MAINT-* (normativ) → GSEPF (kontrollierter Prozess: Development/Security/Release/Maintenance Governance) → Maintenance Engine (M0 Automate / M1 Review / M2-M3 Escalate) → Evidence → Verified State. Maintenance ist Bestandteil der Systemintegritaet, kein organisatorisches To-do.
